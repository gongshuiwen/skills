# Documentation Baseline Maintenance

## 目标

让文档随系统持续演进，以**最小必要的维护成本**保持信息准确、一致、可发现且可追溯；不以文档数量、篇幅或新增文件数衡量产出。

## 适用与边界

- 在功能、接口、配置、架构、部署流程或用户可见行为变化，以及专门的文档维护任务中使用。
- 文档审查嵌入当前变更流程，聚焦受影响内容及必要的交叉引用；不借机大规模整理无关文档。
- 不影响已记录行为、契约或使用方式的纯内部修改，可在评估后**不修改文档**。
- 遵循项目现有文档分类、目录、风格、生成流程及监管或审计留存要求；不强制引入新工具、模板或文档平台。

## 工作流

### 1. 确认变更及文档事实依据

- 识别变更影响的用户操作、公开 API、配置参数、部署命令、架构职责、兼容性或故障处理方式；无关项无需展开。
- 结合已确认需求与契约、代码实现、配置定义、测试及正式设计决策确定事实依据。**当前实现不一定代表正确或预期行为**；有冲突时核实后再改文档。
- 明确区分**已实现/当前有效、计划中、已废弃**的内容；不得把推测、设计草案或尚未交付的能力写成现状。

### 2. 新增文档前先审查现有文档

- 查找受影响的 README、使用指南、API/配置说明、架构文档、部署文档、ADR、CHANGELOG 及索引，确认相关内容的权威维护位置。
- 判断已有内容是否准确、重复、过时、职责混杂、难以发现或缺少必要说明；检查与相邻文档的引用关系。
- **优先维护单一权威来源**：详细规则与参数尽量在一个合适位置维护，其余位置通过摘要和链接引用；允许针对不同受众提供必要但不冲突的概述。
- **新增文档准入检查**：明确独立主题、目标读者、持续参考价值及现有文档不能合理承载的原因；若只需补充一节或更新链接，不新增文件。

### 3. 选择最小必要的维护动作

按实际情况选择，不要求每次都执行全部动作：

| 判断 | 动作 |
| --- | --- |
| 文档准确且仍有用途 | **保留**，不为整理而修改 |
| 现有有效行为或契约变化 | **更新**对应权威文档、示例和必要引用 |
| 内容重复、职责混杂或位置不合理 | **整合/重组**，保留独有信息及可发现性 |
| 当前状态说明已失效且无持续价值 | **清理/归档**，先确认引用、迁移与留存要求 |
| 存在独立且长期有用的信息缺口 | **新增**最小必要文档，并接入适当索引或入口 |

- **当前状态文档与历史记录分离**：README、指南、接口和部署说明应反映当前有效状态；ADR、CHANGELOG、迁移记录等应保留历史，并通过状态标记、后续记录或链接说明取代关系，不静默改写历史。
- 一次性任务总结、临时分析、排障过程或实施流水账默认不纳入长期文档基线；明确有持续参考、审计或用户要求时除外。
- 删除、合并或迁移前确认没有丢失独有知识；修复受影响的入口、相对链接和交叉引用，必要时保留迁移指引。
- 不为减少文件数量强行合并不同受众或职责的文档，也不为“写了文档”而新增无独立信息价值的文件。

### 4. 核验准确性、一致性及可发现性

- 核对涉及的文件路径、命令、配置项、环境变量、API 字段、版本约束和架构关系是否与已确认事实相符；条件允许时实际验证重要命令或示例。
- 检查受影响的导航、相对链接、锚点与交叉引用；如有文档生成源，优先更新源文件而非手改生成产物。
- 对无法验证或仍有分歧的内容明确标注状态与限制，不以猜测补齐细节，也不声称未执行的检查已通过。
- **新增内容价值自检**：确认其填补真实信息缺口、放在正确位置、不会与权威内容形成重复维护；否则优先合并、调整或移除。

### 5. 简要汇报维护结果

- 在常规开发变更说明中简述**保留 / 更新 / 整合 / 归档 / 清理 / 新增**的关键内容及原因；新增文档说明其独立信息价值。
- 列明实际核验的关键命令、示例或链接，以及未核实的内容和已知限制；无文档变更时简述为何无需修改。
- 不为汇报本次工作额外创建长期 Markdown 总结文件，除非明确要求或确有持续使用价值。

## 不可违反的约束

1. 不得把未确认、未实现或计划中的能力描述为当前事实，不得为迎合代码现状而篡改明确的需求或契约。
2. 不得默认通过新增文档文件完成任务；先检查并优先维护现有权威位置。
3. 不得为了精简而静默删除历史决策、重要迁移记录、必要的操作知识或有留存义务的内容。
4. 不得留下已知的互相矛盾的当前状态说明；确有不同版本或环境时明确适用范围。
5. 不得为执行本 Skill 而扩展到无关文档、引入不必要的文档框架或生成低价值任务总结；不以文件数量作为优化目标。
